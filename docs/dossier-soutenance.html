1. Contexte & démarche DevOps

On a fait un forum simple (catégories, sujets, messages) exprès : ce qu'on note ici, ce n'est pas l'appli, c'est la « usine » qui la fabrique et la met en ligne toute seule. Notre objectif depuis le début : qu'un nouveau membre puisse tout lancer en une seule commande, et qu'aucune version ne soit livrée sans avoir été testée automatiquement.

💡 DevOps, en clair : avant, les « Dev » écrivaient le code et le jetaient par-dessus le mur aux « Ops » qui devaient le faire tourner — d'où des bugs et des reproches. DevOps casse ce mur : une seule équipe, des machines qui automatisent le build/test/déploiement, et un retour d'erreur rapide.

Chacun sait lire et réparer le maillon du voisin grâce à la doc et aux PR, ce qui réduit le bus factor (aucune personne indispensable).

2. Pourquoi conteneuriser ? Critère 1 — 30 %

Conteneuriser, c'est mettre l'application et tout ce dont elle a besoin pour tourner (la bonne version de Python, les librairies…) dans une boîte fermée appelée image. Le problème qu'on résout :

💡 L'analogie : un conteneur, c'est comme un plat préparé sous vide : peu importe la cuisine où tu le réchauffes, le résultat est identique. Sans ça, chaque poste a « sa » recette légèrement différente → le fameux « chez moi ça marche ».
Sans conteneurAvec conteneur (Docker)
« Ça marche sur ma machine » — versions de Python/libs différentes selon les postesReproductibilité : la même image tourne à l'identique sur tous les postes et en CI
Installation manuelle, longue, source d'erreurs1 commande (docker compose up) lève toute la stack
Difficile d'isoler API et base de donnéesIsolation : chaque service dans son conteneur, réseau privé entre eux
Rollback compliquéImage taguée par version → on redéploie l'ancienne en secondes
Lien culture DevOps (CALMS · DORA) La conteneurisation sert deux piliers concrets : Reproductibilité (l'image est la même partout, du laptop au registre) et Automation (elle se construit toute seule dans le pipeline). C'est ce qui rend possible une fréquence de déploiement élevée (indicateur DORA) sans casser la prod.

4. Architecture Docker Critère 1 — 30 %

Trois services isolés, reliés par un réseau privé Docker. Seuls les ports utiles sont exposés vers l'hôte ; l'API parle à la base par le réseau interne (jamais exposée à l'extérieur).

Flux : navigateur → nginx (sert le front + reverse-proxy /api pour éviter le CORS) → FastAPI → PostgreSQL (volume = données qui survivent au redémarrage).

4.1 Dockerfile de l'API — multi-stage (image légère)

💡 Multi-stage, en clair : on cuisine dans une grande cuisine pleine d'outils (étape builder), puis on ne sert que l'assiette finale sans tout le bazar de préparation (étape runtime). L'image livrée est donc plus petite et plus sûre (moins de choses = moins de failles possibles).
# ÉTAPE 1 — builder : installe les deps
FROM python:3.12-slim AS builder
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir \
    --prefix=/install -r requirements.txt

# ÉTAPE 2 — runtime : image finale
FROM python:3.12-slim AS runtime
WORKDIR /app
COPY --from=builder /install /usr/local
COPY src/ ./src/
COPY alembic/ ./alembic/  alembic.ini .
EXPOSE 8000
CMD ["sh","-c","uvicorn src.main:app \
     --host 0.0.0.0 --port ${PORT}"]

À expliquer à l'oral :

  • Multi-stage : l'étape builder compile/installe les dépendances ; l'image finale ne récupère que le résultat (/install) — pas les outils de build. Résultat : image plus petite et plus sûre.
  • Base officielle + slim : maj de sécurité suivies, surface réduite.
  • --no-cache-dir : pas de cache pip inutile dans l'image.
  • Couches ordonnées : requirements.txt copié avant le code → le cache Docker ne réinstalle les libs que si elles changent (builds plus rapides).
Limite assuméeLes conteneurs tournent en root (la grille recommande non-root) → identifié comme axe d'amélioration n°1 (ajouter un USER appuser).

4.2 Dockerfile du front — node → nginx

Même principe multi-stage : on build le React avec Node, puis on ne garde qu'un nginx qui sert les fichiers statiques (image finale minuscule, pas de Node en prod).

FROM node:20-alpine AS build      # compile le React
RUN npm ci && npm run build
FROM nginx:alpine AS runtime      # ne garde que le statique + nginx
COPY --from=build /app/dist /usr/share/nginx/html

4.3 docker-compose.yml — l'orchestration locale

Compose décrit les 3 services, l'ordre de démarrage et le stockage, dans un seul fichier.

💡 En clair : Compose est le chef d'orchestre. Au lieu de lancer chaque conteneur à la main dans le bon ordre, on écrit une fois « voilà mes 3 services et comment ils se parlent », et docker compose up joue toute la partition.
services:
  db:
    image: postgres:16-alpine
    environment:                      # injectées depuis .env (hors Git)
      POSTGRES_USER: ${POSTGRES_USER}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
    volumes: [ postgres-data:/var/lib/postgresql/data ]   # persistance
    healthcheck:                      # « la base est-elle prête ? »
      test: ["CMD-SHELL","pg_isready -U ${POSTGRES_USER} -d ${POSTGRES_DB}"]
      interval: 5s   retries: 10

  api:
    build: .
    environment:
      DATABASE_URL: postgresql://...@db:5432/...   # « db » = nom du service = DNS interne
    depends_on:
      db: { condition: service_healthy }            # attend que la base soit healthy
    command: sh -c "alembic upgrade head && uvicorn src.main:app ..."   # migre PUIS démarre

  frontend:
    build: ./frontend
    depends_on: [ api ]

volumes: { postgres-data: {} }        # volume nommé = données qui survivent
networks: { forum-network: { driver: bridge } }
Élément ComposeCe qu'il garantit (à dire à l'oral)
healthcheck + depends_on: service_healthyL'API ne démarre pas avant que la base réponde → pas de crash au boot. Dépendances cohérentes (critère grille).
alembic upgrade head && uvicornLe schéma de la base est migré automatiquement avant le démarrage : zéro étape manuelle.
Volume nommé postgres-dataPersistance : on peut tuer/relancer les conteneurs, les données restent.
Réseau forum-networkL'API joint la base via db:5432 (DNS interne). La base n'est jamais exposée à l'hôte.
Variables ${...} via .envAucun secret dans Git — le .env est dans .gitignore (critère sécurité).
Question type N3 du jury : « un conteneur ne démarre pas, que faites-vous ? » docker compose ps (qui est down) → docker compose logs api (lire l'erreur) → docker compose exec db pg_isready (la base répond-elle ?). Ce réflexe = feedback rapide et diagnostic autonome.

5. La chaîne CI/CD Critère 2 — 30 %

Dès qu'on envoie du code sur GitHub (push), une suite d'étapes se lance toute seule. Si tout passe, l'image de l'API est publiée avec une étiquette unique (le numéro du commit).

💡 En clair : c'est une chaîne de montage automatique. À chaque modification, un robot vérifie le code (lint), lance les tests, contrôle la sécurité, fabrique l'image et la range au dépôt. Si une étape échoue, la chaîne s'arrête et rien n'est livré — l'erreur est attrapée par la machine, pas par l'utilisateur.
ÉtapeOutilPourquoi elle existe
LintruffCode propre et homogène avant tout — étape la plus rapide, on échoue tôt et pas cher (fail fast).
Audit depspip-auditDétecte les failles connues (CVE) dans les dépendances.
Testpytest (18 tests)Vérifie que le code fait ce qu'on attend → fait baisser le change failure rate (DORA).
ScanTrivyScanne l'image construite (failles HIGH/CRITICAL). Règle : on ne publie que ce qu'on scanne.
Build + PushGHCRPublie l'image taguée par SHA → traçable et rollback immédiat sur une version antérieure.
Sécurité — secrets hors Git Le push s'authentifie avec le GITHUB_TOKEN fourni par Actions (jamais commité). Le job d'intégration génère le .env à partir des GitHub Secrets. Aucun mot de passe n'est dans le dépôt.

Pourquoi cet ordre ? (arbitrage à défendre)

Le push est gaté sur lint+test ET scan : on ne publie jamais une image qui n'a pas passé la sécurité. Compromis assumé vitesse ↔ sûreté : on accepte un pipeline un peu plus long pour ne jamais livrer une image vulnérable. C'est le lien direct outillage → fiabilité de livraison.

7. Posture DevOps — culture (CALMS & DORA) Critères 3+4 — 40 %

CALMS

  • Culture : rôles clairs mais poreux, revues par PR.
  • Automation : pipeline complet + migrations auto.
  • Lean : petites PR, fail fast, feedback court.
  • Measurement : pip-audit + Trivy mesurent la sécurité à chaque push.
  • Sharing : README + ce dossier → bus factor réduit.

DORA — ce que notre chaîne améliore

  • Deployment frequency ↑ : image prête à chaque push.
  • Change failure rate ↓ : lint+test+scan bloquent le mauvais code.
  • Lead time ↓ : du commit à l'image publiée, automatique.
  • MTTR ↓ : images taguées par SHA → rollback en secondes.

Limites connues & pistes (à assumer à l'oral)

  • Conteneurs en root → ajouter un utilisateur non-root.
  • Front pas encore scanné donc pas publié (on ne publie que ce qu'on scanne) → ajouter son scan Trivy.
  • Pas de déploiement continu réel (pas de cible de prod) → le « CD » s'arrête à la publication d'image.

8. Antisèche — commandes de la démo

Lancer / vérifier

cp .env.example .env              # 1. config (hors Git)
docker compose up --build -d      # 2. lever la stack
docker compose ps                 # 3. tout est Up (healthy) ?
curl localhost:8000/health        # 4. API vivante
open http://localhost:8000/docs   # 5. Swagger (créer user, login)
open http://localhost:8080        # 6. le front (forum)

Diagnostiquer (si un service est down)

docker compose logs api           # lire l'erreur de l'API
docker compose logs db            # lire l'erreur de la base
docker compose exec db pg_isready # la base répond-elle ?

Nettoyer

docker compose down -v            # arrêt + suppression du volume

9. Glossaire — à réviser la veille

Chaque terme en une phrase + où on l'utilise dans le projet. De quoi répondre du tac au tac aux questions « niveau 1 » du jury (« définissez… »).

ConteneurApplication empaquetée avec tout son environnement (libs, runtime), qui tourne isolée de la machine hôte.→ nos 3 services : api, db, frontend.
Image vs conteneurL'image est le modèle figé (la recette) ; le conteneur est une instance qui tourne (le plat). Une image → plusieurs conteneurs.→ on build l'image API, on la lance en conteneur.
DockerfileRecette qui décrit comment construire une image, étape par étape.→ un pour l'API, un pour le front.
Multi-stageDockerfile en plusieurs étapes : on compile dans l'une, on ne garde que le résultat dans l'image finale → image plus petite et plus sûre.→ builder (deps) → runtime (app seule).
Docker ComposeOutil qui décrit et lance plusieurs conteneurs ensemble depuis un seul fichier docker-compose.yml.→ docker compose up lève toute la stack.
HealthcheckTest périodique « le service est-il prêt à répondre ? » que Docker exécute.→ pg_isready sur la base ; l'API attend qu'elle soit healthy.
VolumeEspace de stockage géré par Docker, qui survit à la suppression du conteneur → la donnée persiste.→ postgres-data garde la base.
Réseau / DNS interneRéseau privé entre conteneurs ; chaque service est joignable par son nom.→ l'API joint la base via db:5432, jamais exposée dehors.
Reverse-proxyServeur qui reçoit les requêtes et les redirige vers le bon service interne.→ nginx sert le front et renvoie /api vers FastAPI (évite le CORS).
CI/CDCI = intégration continue (tester/builder à chaque push) ; CD = livraison continue (publier l'image prête).→ GitHub Actions, du commit à l'image GHCR.
PipelineSuite d'étapes automatiques déclenchées par un événement Git (push, PR).→ lint → test → scan → build → push.
Registre / GHCREntrepôt d'images Docker. GHCR = celui de GitHub, authentifié par le token intégré.→ on y publie l'image API taguée par SHA.
Tag SHAÉtiquette d'image = identifiant exact du commit → on sait quelle version tourne, rollback immédiat.→ ...-api:<sha>.
LintAnalyse du code sans l'exécuter : style, imports inutiles, erreurs probables.→ ruff, première étape (fail fast).
CVEFaille de sécurité publiquement répertoriée (Common Vulnerabilities and Exposures).→ détectées par pip-audit (deps) et Trivy (image) ; on en a corrigé 11.
Migration (Alembic)Script versionné qui fait évoluer le schéma de la base avec le code.→ alembic upgrade head joué au démarrage de l'API.
Secret hors GitMot de passe / clé jamais commité : injecté via .env (local) ou GitHub Secrets (CI).→ .env est dans .gitignore.
Fail fastÉchouer le plus tôt et le moins cher possible (lint avant tests avant build).→ on ne perd pas de temps à builder du code qui ne lint même pas.
CALMSLes 5 piliers DevOps : Culture, Automation, Lean, Measurement, Sharing.→ on cite Automation (pipeline) + Sharing (doc, rôles).
DORA4 indicateurs de perf DevOps : fréquence de déploiement, lead time, taux d'échec, MTTR.→ notre CI fait ↑ la fréquence et ↓ le taux d'échec.
Bus factorNombre de personnes dont le départ bloquerait le projet. Plus il est haut, mieux c'est.→ doc + PR → personne n'est indispensable.
