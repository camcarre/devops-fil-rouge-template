Contexte

1Contexte et objectif

  • Une application de forum : créer des sujets, poster des messages
  • Le vrai travail : la chaîne automatisée autour — développer, construire, livrer, exécuter
  • À livrer : application en conteneurs, lancement reproductible, pipeline automatique, aucun secret dans le code
Ce qu'on a fait : une application de forum, API plus base de données. Pourquoi un sujet aussi simple : pour que l'application ne prenne pas toute la place — l'objectif du module, c'est la démarche DevOps autour, pas le forum lui-même. Le cap qu'on s'est fixé dès le départ : pouvoir tout relancer à l'identique, et ne rien livrer sans test automatique.

Architectureconteneurisation

3Architecture de l'application

Trois services séparés · la base de données reste interne, jamais exposée à l'extérieur

Ce qu'on a fait : on a découpé l'application en trois services séparés — l'interface, l'API et la base de données — qui communiquent sur un réseau privé. Pourquoi séparer plutôt qu'un seul bloc : chaque partie peut être mise à jour ou remplacée sans toucher aux autres, et surtout on a choisi de ne jamais exposer la base de données à l'extérieur — seule l'interface est accessible. Le stockage est conservé même si on redémarre les services.
Conteneurisation30 %

4Mise en conteneurs

  • Chaque partie est empaquetée avec tout ce qu'il lui faut pour fonctionner
  • Construction en deux temps : on prépare, puis on ne garde que le strict nécessaire
  • Résultat : une image plus légère et plus sûre (moins de composants = moins de failles)
Ce qu'on a fait : des fichiers de construction (Dockerfile) en deux étapes : une étape prépare les dépendances, l'autre ne garde que l'application finale. Pourquoi : sans ça, l'image finale traînerait tous les outils de préparation → lourde et plus de failles possibles. On part d'une image Python officielle et allégée (la version « slim », qu'on a préférée à « alpine » qui complique l'installation). Limite qu'on assume : nos conteneurs tournent encore avec les droits administrateur — c'est notre première piste d'amélioration.
Orchestration30 %

5Lancer tout en une commande

  • Un seul fichier décrit les trois services et la façon dont ils se connectent
  • L'API attend que la base soit prête avant de démarrer
  • La base se met à jour automatiquement au démarrage, sans intervention
Ce qu'on a fait : un fichier (docker-compose) qui décrit nos trois services et les lance ensemble. Une seule commande, docker compose up, démarre tout. Pourquoi : n'importe qui dans l'équipe relance l'application complète sans rien installer à la main. On a réglé deux points qui posaient problème : l'API ne démarre qu'une fois la base prête (sinon elle plantait), et les mises à jour de la base s'appliquent toutes seules au démarrage.
Orchestration — l'essentiel du docker-compose
docker-compose.yml
services: db: # base de données image: postgres:16-alpine volumes: [ postgres-data ] # données conservées healthcheck: [ pg_isready ] # la base prête ? api: # notre application depends_on: db: { condition: service_healthy } # attend la base environment: DATABASE_URL: ${POSTGRES_PASSWORD} # secret via .env frontend: # interface web depends_on: [ api ] # démarre après l'API

Extrait des 3 services · les lignes surlignées = démarrage ordonné & secrets hors du code

Ne pas lire ligne par ligne — pointer 3 endroits : 1) healthcheck + depends_on: service_healthy : l'API attend que la base soit prête avant de démarrer. 2) le volume postgres-data : les données restent même si on supprime le conteneur. 3) le DATABASE_URL vient d'une variable (.env), jamais écrit dans le fichier. Préciser : « c'est un extrait — le fichier complet est dans le dépôt ; ici je montre les 3 services et les lignes qui comptent. »
Intégration & livraison continues30 %

6La chaîne automatique

À chaque envoi de code, tout s'enchaîne automatiquement · règle : on ne publie que ce qui a été contrôlé

Ce qu'on a fait : un pipeline (GitHub Actions) qui se déclenche à chaque envoi de code sur la branche principale. Pourquoi chaque étape : vérification du code et tests (s'assurer que ça marche), analyse de sécurité, construction de l'image, puis publication. La règle qu'on s'est fixée : on ne publie que ce qu'on a contrôlé. L'image est rangée sur le registre de GitHub (GHCR — choisi plutôt que Docker Hub car déjà intégré, rien à configurer), identifiée par sa version pour pouvoir revenir en arrière.
Sécurité

7Sécurité

  • Aucun mot de passe dans le code : les informations sensibles sont dans des fichiers séparés, gardés hors du dépôt
  • Les images et les dépendances sont analysées automatiquement à chaque envoi
  • 11 vulnérabilités connues corrigées en mettant les dépendances à jour
Ce qu'on a fait : aucun secret n'est écrit dans le code. En local, ils sont dans un fichier ignoré par Git ; dans le pipeline, ils viennent du coffre de GitHub (GitHub Secrets), et la publication utilise un jeton fourni automatiquement. Pourquoi : un secret commité, même dans un dépôt privé, est considéré compromis. On a aussi branché deux analyses automatiques (Trivy pour les images, pip-audit pour les dépendances) — c'est ce qui nous a permis de repérer et corriger 11 vulnérabilités.
Démonstrationdéploiement

8Démonstration — déploiement

  • Une commande lance toute l'application
  • L'API répond (vérification de bonne santé)
  • La documentation de l'API est générée automatiquement
  • Le forum s'affiche dans le navigateur
Faire la démo, pas seulement la décrire : 1) lancer docker compose up (ou déjà lancé). 2) montrer que les trois services tournent et sont « en bonne santé ». 3) ouvrir l'adresse de vérification (/health). 4) ouvrir la documentation (/docs), créer un compte, se connecter. 5) montrer le forum. Insister : « l'API n'a démarré qu'une fois la base prête, c'est automatique. » Prévoir des captures en secours si le réseau lâche.

  • tout est passé sur le projet

L'image publiée

  • rangée sur le registre GitHub

Montrer l'écran GitHub : 1) onglet « Actions » → le dernier passage tout au vert (chaque étape cochée). 2) onglet « Packages » → l'image publiée, avec son numéro de version. Dire : « l'image est publiée automatiquement, identifiée par la version exacte du code, donc on sait toujours ce qui tourne et on peut revenir en arrière. » Rappeler : aucun mot de passe n'a été nécessaire dans le code, tout passe par le coffre de GitHub.

Après
Repérée et corrigée à partir des messages d'erreur

L'erreur a été vue par la chaîne avant qu'un utilisateur ne la rencontre

L'histoire à raconter (très valorisée par le jury) : « Notre chaîne était annoncée comme fonctionnelle, mais en réalité une dépendance n'existait pas et bloquait tout. On a vu l'échec, lu les messages d'erreur, corrigé, et relancé : tout est repassé au vert. Au passage, on a mis les dépendances à jour et corrigé 11 vulnérabilités. » La conclusion à appuyer : l'intérêt de l'automatisation, c'est que l'erreur est attrapée par la machine, pas par un utilisateur en production.
Démarcheposture DevOps

11Notre démarche

Ce qu'on gagne

  • Reproductible : identique sur tous les postes
  • Automatisé : moins d'erreurs humaines
  • Tracé : on sait quelle version tourne

Limites et pistes

  • Conteneurs avec droits administrateur
  • Interface pas encore analysée
  • Mise en cache du pipeline
Relier nos choix à un objectif (et pas à une liste d'outils) : « On n'a pas empilé des outils pour le plaisir — chaque brique sert à livrer souvent, sans casser, et à réparer vite. » Le lien concret : le pipeline et le registre nous laissent livrer quand on veut ; les tests et l'analyse réduisent les erreurs ; les images versionnées permettent de revenir en arrière. Et côté équipe, la relecture et la documentation font que personne n'est indispensable. Assumer les limites montre qu'on est lucides.
